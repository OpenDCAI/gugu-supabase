# Project files: local metadata and encrypted on-demand transfer

Backend mechanisms are developed in separate commits. Client resolution and its product acceptance remain separate work; database and source tests do not prove desktop or Android behavior.

The combined permanent-retention and project-transfer diff uses one shared resolver, quota ledger and collector. Runtime accounting against its integration base is:

Tests, documentation, the integration runner and generated Deno lock are reported separately. Existing version snapshots gain a constrained local-revision pointer, preserving exactly one body provider per version; no placeholder cloud blob stands in for a local file. Enabling proactive cloud upload permits the host's next version through the existing managed upload path, while remote mutations remain refused. Historical pinned local versions retain their original provider.

`file_project_policy_as` requires the actual project binding, device ownership and group administrator membership. Proactive upload defaults to false; temporary transfer and its retention are separate explicit settings. An unbound or removed project cannot resolve a local revision even if an obsolete policy survives. Absolute roots are not included in the file resolver response.

`file_device_publish` records a device, project, canonical relative path, SHA-256, size, name and content type for each immutable file version. Negative sizes, traversal, absolute paths, Windows drive/UNC paths, control characters and ambiguous separators are refused atomically. Existing documents and files belonging to another group cannot be overwritten. A version conflict cannot silently replace metadata. The host must still perform its existing realpath/root fence and verify SHA before serving bytes: metadata alone is not filesystem authorization.

Composer preparation does not publish files. Ordered commit passes the message to the same `file_device_publish` entry point, which creates the revision and sends its exact pinned message in one transaction. A failed message, recipient, payload or idempotency check rolls back the revision and workspace row too. The entry point is `SECURITY INVOKER`, so `send_message_idempotent` runs with the caller's original message RLS. Calling it from a definer would bypass that RLS; the negative recipient contract protects this boundary. Thread fields retain the existing sender behavior; this entry point does not introduce a second thread ACL or claim that SQL rejects an unregistered thread ID.

One new private schema, `file_private`, holds the original definer revision implementation. Exclude this schema from every PostgREST exposed-schema configuration. PUBLIC and anon have no access; authenticated needs schema usage and execute on this one kernel because an invoker cannot call a function without its caller's permission. A database SQL session holding the authenticated role can therefore call the kernel directly. That kernel has exactly the prior bound-device, owner and group checks, performs no message send, and gives no permission beyond the former public publication API. No dedicated database role or duplicate message ACL is introduced.

`file_resolve_as` is the common metadata entry point for local files, managed objects, pinned message versions and private task attachments. It delegates actor, membership, message visibility and managed-object permissions to the existing helpers. It returns no signing URL, data key, arbitrary-path read or device write capability. Managed references retain their expired status. The same HTTP metadata endpoint accepts `ref` or a bounded `refs` batch of 1–200 exact references; both normalize to the same existing ACL calls. Every input is validated before an ACL call, and batch responses echo the exact reference for safe fan-out. There is no signing, budget reservation or shared access-decision cache in metadata batching. Message pinning accepts local metadata through the original attachment trigger without inventing a cloud blob.

Existing mutation APIs cannot modify a local reference on behalf of another reader. Even the owner cannot create an unindexed file version through a cloud rename/replace: local changes must first be published by the host. Existing cloud files retain their existing mutation permissions. A metadata deletion does not delete a host filesystem path.

All new tables have RLS and no direct API grants. Only intended metadata/publish functions are authenticated; internal trigger/envelope functions remain closed. Tests cover these grants both on installation and at the service contract boundary.

Temporary generations use the existing quota reservations and immutable provider forms. Their random `temporary/<group>/<file>/<version>/<SHA>/<generation>` objects are registered in the original blob inventory with logical bucket `temporary`; they share the configured physical object provider. Commit verifies ciphertext size and SHA by streaming before storing the service-only file key. Database and object-storage backups together can decrypt these files; this protects against storage disclosure, not the service operator.

The same `file_transfer_download_as` transaction authorizes metadata and reserves actual ciphertext bytes. Its private context binds the original reference, actor and generation. Key return is service-only, bound to the same authenticated account and unexpired reservation, and rechecks the exact reference and current policy. A read completion affects retention only; it does not refund download allowance. Retained generations renew only on a fresh authorized download, with a 30-day absolute ceiling. Read-once generations bind one download identity.

Encrypted temporary reads bypass CDN. `ali-oss@6.23.0` (MIT) supplies its official `signatureUrlV4`; no new signature algorithm is implemented. The SDK signs its current time, so retries use the reservation's remaining lifetime and reject any actual signature deadline beyond that reservation. The origin signature includes the request throttle and download attribution identifier. The SDK is an edge-function dependency and does not enter the client installation package. The Deno lock pins its transitive dependencies.

If provider capabilities cannot be verified, acceptance fails closed and does not expose an upload form. A previously reserved allowance remains held until trusted terminal evidence permits closure. An expired permit plus HEAD 404 still does not prove that a previously accepted upload cannot finish late. Temporary uploads write their final random position directly: operators must not apply ordinary staging-prefix cleanup to active generations. Physical cleanup belongs to the original blob collector; an unverified abandoned upload must not receive an automatic financial refund.

The retention group connects expiry, revocation and temporary-only LRU to the original blob garbage collector. Both its scheduled tick and manual HTTP collection discover retired generations. Fresh authorized reads renew retention, with an absolute 30-day ceiling; metadata views and retries do not. Read-once completion retires the key without refunding download bytes. Changes to a file version, source visibility, project binding, membership or transfer policy invalidate keys immediately and queue physical collection on the next bounded pass.

`temporary_group_bytes` is a required deployment parameter, with the same group overrides as the existing storage quota. It counts confirmed temporary inventory and held temporary upload allowances; permanent storage has its independent existing group budget. When either group budget lacks room, only ready temporary generations are LRU candidates. Retirement never releases capacity. Acceptance retries after the original collector confirms physical deletion; active capabilities can defer collection and keep acceptance refused. Permanent files never enter this LRU.

An unverified placeholder is registered in the existing blob table when the upload permit is issued, without claiming verified size or adding physical inventory. Source deletion can therefore enqueue the exact object even before commit. The original collector protects an upload until its permit expires, including when the source row has already disappeared. Commit updates only the same live placeholder after streamed verification, never a blob already being collected. Cleanup of an abandoned upload does not itself refund its allowance: trusted terminal evidence is still required. No second worker, quota ledger, persistence table or restore RPC is introduced.

The client implementation will have one resolver before any cloud metadata lookup: local loopback, the reader's already-open owner SSH link, then encrypted temporary cloud transfer. Expired cards and ordinary re-upload belong to the separate permanent-file expiry change, not this resolver change.

The full contract runner isolates quota policy and next-idle-pass GC assertions from unrelated object-writing suites. The original GC concurrency suite still uses real concurrent database transactions, with every original assertion preserved. This separation does not replace or remove concurrency coverage: collection legitimately skips a busy global quota lock, so another suite's incidental writer cannot stand in for the test's intended idle pass.

## One backend activation event

The budget enforcement code is already part of the integration branch. Deploying any later function bundle, including this combined lifecycle change, activates that same enforcement. Do not schedule an intermediate deployment while a previous compatible function bundle remains active. The lifecycle rollout and budget reactivation are one switchover, gated by the same operator checklist:

1. Inventory the versions of actually running desktop, mobile and per-account server processes, with fresh observations. A downloaded package or desired-version record is not evidence. Exercise upload, commit and verified download for every active ingress. All known active uploaders must send the complete bounded protocol; unknown and incompatible active processes block activation. Document the explicitly accepted cutoff for offline legacy clients.
2. Review and write the complete global `chat.file_transfer_limits` settings while intake is held: storage/download global, account and group limits, file ceiling, permit lifetime, signing lifetime/counts, link throttle, expiry threshold/idle interval, warning threshold and temporary-group capacity. Keep `paused` true until the cutover. Verify the real provider ceiling, required read permissions and both cached and uncached throttling. A rollback function bundle may not honor `paused`; an operational intake hold is required during drain.
3. Reconcile authoritative physical inventory, exact object ownership, held upload permits and trusted completed download logs. Conservatively deduct unassignable prior usage from the available monthly budget. Missing observations, an expired link or one HEAD 404 do not release reservations. Keep original ledgers and a configuration snapshot.
4. Drain previously issued capabilities and accepted uploads using trusted terminal evidence, finish the inventory delta, then deploy the reviewed combined source once through the existing deployment lock. Verify migrations and functions together; do not reapply or rewrite released migration history.
5. Unpause and run real small-file upload/commit/download/SHA canaries plus exhausted-budget, full-storage and account-isolation refusals before removing the intake hold. On any failed gate, retain the hold or restore the single prior compatible function bundle and configuration snapshot. No compatibility dispatch or server restart is introduced.

Fresh installation and an upgrade from the real integration base must install identical guarded sharing functions. Managed-file rename/move version changes retain the original content timestamp; only a new local publication without a cloud blob extends that content-edit rule. Original negative ACL and metadata-only timestamp assertions remain unchanged.
