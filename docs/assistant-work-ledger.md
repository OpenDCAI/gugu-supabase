# Assistant work ledger and delivery contract

Refs OpenDCAI/gugu#428. This is account data, independent of an execution host's session directory.

There are two durable tables: `identity.assistant_work` and `identity.assistant_work_events`. An event is also the only delivery outbox entry. Runtime code must not create another persistent queue. A transaction that creates or terminates work also inserts its delivery event; neither can commit alone.

## Write and delivery API

All names below are in the `identity` schema. All writers require the owner's authenticated session and a current owned `runtime_instances` lease. An assistant is an owned agent with a ready/completed `assistant` provision. Reads require only the account, never a runtime lease or an online device.

`assistant_work_commit(p_assistant text, p_runtime_instance_id text, p_operation_id uuid, p_work_id uuid, p_task jsonb, p_events jsonb)` creates work when `p_task` is present and atomically appends/enqueues one or more events. Later reports pass null for `p_task`. A repeated operation or message ID must have the same immutable request; a mismatch is rejected. It returns `{work_id, event_ids, outcome, terminal_version}`. A source failure is an error, never an empty success.

Task shape: `{title, coordinator_session_id, executors:[{session_id, device_id, agent_user_id?}], source_link?}`. The coordinator device is derived from the runtime lease. Each executor is an owned device; any supplied agent must belong to that owner/device. IDs are Gugu session IDs, not provider transcript IDs. The dispatch host must allocate the child session ID before submitting its first event.

Event shape: `{message_id, kind, from_session_id, from_device_id, to_session_id, to_device_id, content?, attachment_refs?, source_chat_id?, source_message_id?, executor_session_id?, reason_code?}`. Kinds: `dispatch`, `progress`, `question`, `completed`, `cancelled`, `failed`, `blocked`. `content` is direct-message text; an existing cloud message uses the source pair instead and is read under its original visibility rules. Attachment references are either `{item_id}` for an existing workspace item or the existing `SessionAttachmentRef` shape `{attachment_id,file_name,sha256,size_bytes,content_type}`. Native receipts are checked against their original owner, sending session, addressed receiving agent, live blob and exact metadata. Do not copy bytes, local paths or signed URLs into the ledger. `executor_session_id` attributes a host-generated reconciliation result to the executor. Endpoints and actors are checked against the stored task. Platform acceptance time and event order are generated by the database. Executor terminal outcomes cannot be overwritten by later progress or conflicting terminal results. A multi-executor work item ends only after every executor has a terminal result.

`assistant_work_outbox_claim(p_runtime_instance_id text, p_limit integer = 20, p_lease_seconds integer = 60)` returns `{events:[...]}` with `lease_token`, `lease_until`, the original stable message ID, endpoints, body/references and terminal version. Any current owned runtime can deliver to the named destination; concurrent claimers cannot own the same lease. Unexpired claims are skipped; expired claims can be reclaimed with a different token.

`assistant_work_outbox_settle(p_runtime_instance_id text, p_message_id uuid, p_lease_token uuid, p_stage text, p_error_code text = null, p_retry_after_seconds integer = 5, p_receipt jsonb = '{}')` accepts `executor_admitted`, `assistant_admitted`, `retry`, or `abandoned`. Admission requires the current unexpired token; repeating an already successful confirmation with that token is idempotent. Retry releases the claim, sets a future availability time and increments `failed_attempts`; claim/expiry only increment `attempts`. Abandonment requires an error category, stops further automatic claims and retains the original evidence. Pass `{failure_observed:true}` when the abandonment itself follows a real failed attempt. The pump abandons after 24 hours or 100 actual failures, whichever comes first; retry delays are capped at five minutes. Receipt metadata may bind a previously unknown executor `agent_user_id`, after ownership/device validation. Admission means the destination host durably accepted the message, not that a model finished the task.

`assistant_work_owner_delivered(p_assistant text, p_runtime_instance_id text, p_message_id uuid, p_owner_chat_id text, p_owner_message_id text, p_receipt_kind text = 'result')` records a separate owner receipt after assistant admission. The cited cloud message must actually have been committed by the assistant in a conversation visible to its owner. It does not infer owner delivery from runtime idle, result persistence, or assistant admission. For `p_receipt_kind='abandonment_notice'`, it instead records `abandonment_notified_at` and the failure-notice message, without changing `owner_delivered_at` or pretending the original task/result reached its destination. `assistant_work_abandoned(p_runtime_instance_id text,p_limit integer=100)` discovers abandoned events still requiring that notice after restart. Send notices using a deterministic cloud message key for work ID, recipient and terminal version, then persist the receipt; concurrent/restarted senders must reuse that key.

An executor's own terminal report supersedes a coordinator's inferred failure and is always enqueued with its attachments. A later coordinator inference cannot change an authoritative executor outcome. Only contradictory terminal outcomes both authored by that executor are rejected; repeated identical outcomes may carry additional evidence. Claim results include `terminal_origin`, `assistant_user_id`, `work_outcome`, `work_terminal_version` and `work_executor_outcomes`, allowing the pump to suppress obsolete inferred notifications while still delivering genuine results.

The ledger author owns these tables/RPCs, dispatch/terminal write hooks and panel/mobile readers. The reliable-delivery author owns enqueue orchestration, the claim/settle pump, reachability-aware wakeup and missing-delivery reconciliation. Both use these same event rows and message IDs.

## Reads, counts and history

`assistant_work_list(p_assistant text, p_before bigint = null, p_limit integer = 50)` pages work by its immutable creation sequence. `assistant_work_history(p_assistant text, p_work_id uuid, p_after bigint = 0, p_limit integer = 100)` pages collaboration by database sequence. Reads have no side effects. No transcript tools or model token streams are stored here. Current status remains the existing cloud agent presence; it does not decide work completion.

The normal single-executor path has five business commits: dispatch, executor admission, terminal result, assistant admission, owner delivery. Claim leases and failed-attempt scheduling are additional queue-maintenance updates, not additional collaboration events; RPC/SQL write totals therefore exceed five when delivery uses a lease. Each actual progress/question adds one business event; repeated IDs add none. Reading lists/history and receiving a live token/tool stream add no writes.

Already uploaded history is displayed immediately. Natural host activity can backfill old evidence without user-facing synchronization labels. Missing old evidence is never fabricated. Removing a directory observation, archiving a local session or moving the assistant does not delete the ledger.

Development, migration rehearsals and trial use stay on an isolated local Supabase on the owner's development machine. No shared or production database is changed by this branch. Client/server/mobile trial validation must exercise a model request, a file transfer and direct cloud-ledger reads before final acceptance.

History pages also return `work` (the same public task projection as list, without `initial_task`). A result sender reads coordinator/executor endpoints by assistant + work_id without attaching to any device or scanning completed tasks.

## Historical admissions

`assistant_work_import(p_assistant text,p_runtime_instance_id text,p_work_id uuid,p_task jsonb,p_events jsonb)` upgrades evidence from an awake host. It requires the same account and current owned runtime as ordinary writes. Historical task input additionally names `coordinator_device_id`; each executor includes its real `agent_user_id`. The original work/message IDs, exact direct-message content and `occurred_at` are required. Each event supplies `receipt_kind=received` (runtime must be the recipient) or `sent_admitted` (runtime must be the sender and possess its existing successful delivery receipt). The host must recheck current local data permissions before upload. Missing or ambiguous evidence is skipped.

Imported events are already `admitted`, never enter the delivery pump, and never rerun an old task or manufacture an owner receipt. `platform_received_at` remains the current database receipt; `occurred_at` preserves the original time for display. Repeating a message is idempotent; a conflicting original message ID is rejected. Importing an already live queued event does not mark it delivered. Additional targets can extend only a legacy work item, never an immutable new assignment. Existing executor terminal authority and late true-result rules still apply.

This additive migration changes only the two existing tables (one historical-time field and one legacy-work marker) and adds a restricted RPC. It has been exercised on the isolated my-laptop fixture with 28 targeted database tests; actual desktop/server/phone trial acceptance remains separate.
